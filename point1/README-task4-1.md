# 2. Общая модель памяти процесса

Программа в Linux работает не с физической памятью напрямую, а внутри
**своего виртуального адресного пространства**.

Ядро описывает это адресное пространство как набор областей памяти
(**VMA, Virtual Memory Area**), каждая из которых имеет:

- диапазон виртуальных адресов
- права доступа (`r`, `w`, `x`)
- источник отображения (файл или anonymous memory)

Файл

``` bash
/proc/<pid>/maps
```

показывает текущие отображения памяти процесса.

Типичная схема адресного пространства:

``` text
[text / code]      -> машинный код программы
[rodata]           -> read-only данные, строковые литералы, константы
[data]             -> инициализированные глобальные и static данные
[bss]              -> неинициализированные глобальные и static данные
[heap]             -> динамическая память (malloc)
[mmap regions]     -> библиотеки, анонимные отображения, mmap
[stack]            -> стек вызовов функций
```

# 3. Что показывают nm, readelf и /proc/<pid>/maps

Нужно различать три уровня.

## 3.1 ELF-секции

Их показывают:

``` bash
readelf -S lab4
nm -n lab4
readelf -s lab4
```

Основные секции:

секция       назначение
------------ -------------------------------------------
`.text`      код программы
`.rodata`    read-only данные
`.data`      инициализированные изменяемые данные
`.bss`       неинициализированные данные

## 3.2 ELF-сегменты

При запуске ядро загружает не секции по отдельности, а **segments**
через записи `PT_LOAD` в program header table.

Именно поэтому один и тот же файл программы в
`/proc/<pid>/maps` обычно виден несколькими строками:

- `r-xp` --- код
- `r--p` --- read-only данные
- `rw-p` --- изменяемые данные

## 3.3 Runtime-отображения

`/proc/<pid>/maps` показывает уже не структуру ELF-файла, а **живую карту
памяти процесса**.

То есть:

- `readelf` / `nm` --- что лежит в файле
- `/proc/<pid>/maps` --- что реально отображено в память процесса

# 4. Размещение переменных по областям памяти

## 4.1 Локальные переменные

Обычные локальные переменные функции имеют **automatic storage
duration** и обычно располагаются в стековом кадре функции.

Пример:

``` c
int local_var = 10;
```

Такие адреса попадают в область:

``` text
[stack]
```

## 4.2 Статические переменные в функции

Переменная вида:

``` c
static int static_var = 20;
```

видна только внутри функции, но по времени жизни она существует всё
время работы процесса.

Поэтому она располагается не на стеке, а обычно в:

- `.data`, если инициализирована
- `.bss`, если не инициализирована

## 4.3 Константы в функции

Локальная `const`-переменная:

``` c
const int local_const = 30;
```

не обязана находиться в `.rodata`.

Если это обычный локальный объект и у него берётся адрес, компилятор
может положить его на стек. Именно это и наблюдалось в эксперименте:
локальная `const` имела адрес в `[stack]`.

## 4.4 Глобальные переменные

``` c
int g_init = 42;      // .data
int g_uninit;         // .bss
const int g_const=100; // .rodata
```

Типичное размещение:

объект        секция
------------- ------------------------
`g_init`      `.data`
`g_uninit`    `.bss`
`g_const`     `.rodata`

## 4.5 Строковые литералы

Строковые литералы обычно лежат в `.rodata`.

Важно различать:

``` c
const char *g_str = "global string literal";
```

Здесь:

- `g_str` --- это **глобальный указатель**, он сам обычно в `.data`
- строка `"global string literal"` --- read-only объект в `.rodata`

То же самое для локального указателя:

``` c
const char *local_str = "local string literal";
```

- `local_str` как переменная --- обычно на стеке
- строковый литерал --- в `.rodata`

# 5. Сопоставление адресов с /proc/<pid>/maps

Во время работы программы нужно посмотреть:

``` bash
cat /proc/<PID>/maps
```

и определить, в какой диапазон попадает каждый адрес.

Типичная интерпретация:

область в maps      что означает
------------------- --------------------------------------
`[stack]`           стек процесса
`[heap]`            куча процесса
`r-xp <file>`       код программы или библиотеки
`r--p <file>`       read-only данные
`rw-p <file>`       изменяемые данные программы

Пример интерпретации результатов:

- `local_var` -> `[stack]`
- `local_const` -> `[stack]`
- `static_var` -> `rw-p`-отображение файла программы
- `g_init` -> `rw-p`-отображение файла программы
- `g_uninit` -> `rw-p`-отображение файла программы
- `g_const` -> `r--p`-отображение файла программы
- строковые литералы -> `r--p`-отображение файла программы

# 6. Что показали nm и readelf

В эксперименте были получены типичные результаты:

``` text
R g_const
D g_init
d static_var.0
D g_str
B g_uninit
```

Расшифровка `nm`:

обозначение    смысл
-------------- ---------------------------------
`R`            read-only data
`D` / `d`      initialized data
`B` / `b`      bss / uninitialized data

По `readelf -s` было видно:

- `g_const` -> `.rodata`
- `g_init` -> `.data`
- `g_str` -> `.data`
- `static_var.0` -> `.data`
- `g_uninit` -> `.bss`

Это совпало с `maps`:

- `.rodata` попала в `r--p`
- `.data` и `.bss` попали в `rw-p`

# 7. Стек

## 7.1 Что хранится на стеке

Стек используется для:

- локальных автоматических переменных
- адресов возврата
- служебных данных вызова функций
- сохранённых регистров

Для каждой активной функции обычно существует **stack frame**.

## 7.2 Почему нельзя возвращать адрес локальной переменной

Пример:

``` c
int *return_local_address(void) {
    int local_in_func = 12345;
    return &local_in_func;
}
```

После выхода из функции её локальная переменная прекращает существование,
потому что время жизни объекта ограничено выполнением функции.

Возвращённый указатель становится **dangling pointer**.

Дальнейшее использование такого указателя приводит к:

- выводу старого значения
- выводу мусора
- `NULL`
- `Segmentation fault`

Все эти варианты являются проявлением **undefined behavior**.

# 8. Куча

## 8.1 Что такое куча

Куча --- это отдельная динамическая область памяти процесса, из которой
allocator выдаёт память через `malloc()`.

Куча не является частью секций `.data` и `.bss`.

`.data` и `.bss` --- это статические данные образа программы,
а heap используется для объектов, создаваемых во время выполнения.

## 8.2 malloc и free

### malloc

`malloc(size)` выделяет блок памяти заданного размера и возвращает
указатель на начало пользовательской области.

Внутри allocator работает с **chunk** --- внутренними блоками памяти, у
которых есть:

- служебные метаданные
- пользовательская область (payload)

### free

`free(ptr)` возвращает этот chunk allocator'у.

После `free(ptr)` память больше не принадлежит программе, и доступ к ней
является ошибкой.

## 8.3 Откуда allocator берёт память

Allocator получает память у ОС двумя основными способами:

- через `brk()` --- расширение классической heap-области
- через `mmap()` --- создание новых отображений памяти

Исторически `brk()` двигает **program break**, то есть границу,
определяющую конец data segment / heap-области процесса.

## 8.4 Внутренние термины allocator'а

термин         смысл
-------------- ------------------------------------------------
`chunk`        внутренний блок allocator'а
`arena`        большая область памяти под управление allocator'а
`bin`          корзина свободных chunk'ов
`tcache`       локальный cache свободных chunk'ов потока
`top chunk`    верхний большой свободный chunk arena
`split`        разделение большого свободного chunk'а
`coalesce`     слияние соседних свободных chunk'ов

# 9. Эксперимент с кучей

Использовалась функция, которая:

1.  выделяет буфер 100 байт
2.  записывает в него строку
3.  печатает строку
4.  освобождает буфер
5.  печатает буфер повторно
6.  выделяет второй буфер
7.  записывает строку
8.  печатает адрес и содержимое
9.  формирует указатель на середину буфера
10. делает `free()` по этому указателю

Типичный результат:

``` text
buf address               : 0x56e25cc576b0
buf content before free   : hello world
buf content after free    : W...n
buf2 address              : 0x56e25cc576b0
buf2 content              : hello world
middle pointer            : 0x56e25cc576e2
free(): invalid pointer
Aborted (core dumped)
```

## Объяснение

### После free появился мусор

После `free(buf)` доступ к `buf` стал **use-after-free**.

Allocator получил chunk обратно и мог использовать его под свои
внутренние структуры.

### Второй malloc вернул тот же адрес

Allocator переиспользовал freed chunk подходящего размера.

### free по указателю на середину упал

`free()` должен получать **ровно тот адрес**, который вернул `malloc()`.

Указатель на середину блока не позволяет allocator'у корректно найти
метаданные chunk'а, поэтому программа завершилась с ошибкой.

# 10. Переменные окружения

## 10.1 Что такое environment

Переменные окружения принадлежат **конкретному процессу**.

Они передаются новому процессу через `execve()` как массив строк
вида:

``` text
NAME=value
```

## 10.2 Как использовалось в работе

В shell перед запуском программы задавалось:

``` bash
export LAB4_ENV=first_value
```

В программе:

1.  `getenv("LAB4_ENV")` считывал текущее значение
2.  `setenv("LAB4_ENV", "second_value", 1)` изменял его
3.  повторный `getenv()` показывал уже новое значение

Типичный вывод:

``` text
LAB4_ENV before change       : first_value
LAB4_ENV after change        : second_value
```

## 10.3 Почему после завершения программы в bash всё осталось как было

Потому что программа изменяла **своё** окружение, а не окружение
родительского shell.

Направление наследования только одно:

``` text
bash -> дочерний процесс
```

обратно изменения не передаются.

То есть после завершения программы:

``` bash
echo $LAB4_ENV
```

в bash остаётся старое значение:

``` text
first_value
```

## 10.4 Что значит "задать переменную навсегда"

Это не означает, что она где-то хранится как глобальная системная
переменная процесса навсегда.

Обычно это значит, что команда `export ...` добавляется в startup files
shell, например:

- `~/.bashrc`
- `~/.profile`
- `~/.bash_profile`
- `/etc/profile`

Тогда при запуске shell эта переменная создаётся снова.

# 11. Выводы

В ходе работы было установлено следующее.

1.  Локальные автоматические переменные располагаются на стеке.
2.  `static`-переменные функции ведут себя как глобальные по времени
    жизни и располагаются в `.data` или `.bss`.
3.  Глобальные инициализированные данные попадают в `.data`.
4.  Глобальные неинициализированные данные попадают в `.bss`.
5.  Глобальные константы и строковые литералы обычно попадают в
    `.rodata`.
6.  `/proc/<pid>/maps` показывает runtime-карту памяти процесса, а
    `nm/readelf` показывают структуру ELF-файла.
7.  Возврат адреса локальной переменной приводит к dangling pointer и
    undefined behavior.
8.  После `free()` память больше не принадлежит программе.
9.  Освобождённый chunk может быть повторно выдан следующим `malloc()`.
10. `free()` можно вызывать только по адресу начала блока.
11. Переменные окружения принадлежат текущему процессу и не изменяют
    окружение родительского shell.

# 12. Возможные вопросы на защите

## Почему local_const оказался на стеке, хотя это const?

Потому что `const` не означает автоматически размещение в `.rodata`.
Если это локальный объект функции и у него берётся адрес, он может быть
размещён в стековом кадре.

## Почему g_str находится в .data, а сама строка --- в .rodata?

Потому что `g_str` --- это изменяемый указатель как объект данных, а
строковый литерал --- отдельный read-only объект.

## Почему g_uninit не хранится как обычные байты в файле?

Потому что `.bss` предназначена для неинициализированных объектов.
Память под неё создаётся при загрузке и зануляется ядром.

## Почему malloc вернул тот же адрес после free?

Потому что allocator переиспользовал freed chunk подходящего размера.

## Почему free(buf + 50) некорректен?

Потому что allocator ожидает адрес начала chunk'а, возвращённый
`malloc()`. Указатель на середину блока не подходит.

## Почему setenv внутри программы не меняет значение в bash?

Потому что программа меняет только окружение собственного процесса, а не
окружение родительского shell.
