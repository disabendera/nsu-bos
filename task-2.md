# Пояснение всех системных вызовов

------------------------------------------------------------------------

## 1. execve

``` text
execve("./hello_printf", ["./hello_printf"], envp)
```

Загружает и запускает новый ELF-бинарный файл.

Ядро: — проверяет формат файла, — создаёт новое адресное пространство, —
формирует стек процесса, — копирует `argv` и `envp`, - передаёт
управление точке входа программы.

------------------------------------------------------------------------

## 2. brk

``` text
brk(NULL)
brk(new_address)
```

Управляет границей кучи (heap) процесса.

-   `brk(NULL)` --- возвращает текущий конец кучи\
-   `brk(addr)` --- изменяет границу кучи

Используется аллокатором памяти (`malloc`).

------------------------------------------------------------------------

## 3. mmap

``` text
mmap(addr, length, prot, flags, fd, offset)
```

Создаёт отображение памяти в адресном пространстве процесса.

Используется для: - загрузки библиотек (`libc.so`) - создания анонимной
памяти - размещения сегментов ELF

------------------------------------------------------------------------

## 4. munmap

Удаляет ранее созданное отображение памяти.

------------------------------------------------------------------------

## 5. mprotect

Изменяет права доступа к страницам памяти: - `PROT_READ` -
`PROT_WRITE` - `PROT_EXEC`

Используется загрузчиком для защиты сегментов.

------------------------------------------------------------------------

## 6. openat

Открывает файл и создаёт файловый дескриптор.

Используется для загрузки `ld.so.cache` и `libc.so.6`.

------------------------------------------------------------------------

## 7. close

Закрывает файловый дескриптор.

------------------------------------------------------------------------

## 8. read

Читает данные из файлового дескриптора в память процесса.

------------------------------------------------------------------------

## 9. pread64

Читает данные из файла по указанному смещению, не изменяя текущую
позицию чтения.

Используется загрузчиком ELF.

------------------------------------------------------------------------

## 10. fstat

Получает информацию о файле по файловому дескриптору: - тип - размер -
права доступа

------------------------------------------------------------------------

## 11. access

Проверяет наличие и доступность файла.

------------------------------------------------------------------------

## 12. arch_prctl

Архитектурно-зависимый системный вызов (x86_64).\
Настраивает регистр FS для TLS (thread-local storage).

------------------------------------------------------------------------

## 13. set_tid_address

Сообщает ядру адрес хранения ID потока.

------------------------------------------------------------------------

## 14. set_robust_list

Регистрирует список robust-futex для корректного завершения потоков.

------------------------------------------------------------------------

## 15. rseq

Регистрирует restartable sequences для оптимизации операций в
user-space.

------------------------------------------------------------------------

## 16. prlimit64

Получает или устанавливает лимиты ресурсов процесса.\
В данном случае --- лимит размера стека.

------------------------------------------------------------------------

## 17. getrandom

Получает случайные байты из ядра.\
Используется glibc для инициализации внутренних структур.

------------------------------------------------------------------------

## 18. write

``` text
write(1, "Hello world\n", 12)
```

Записывает данные в файловый дескриптор.

-   `fd = 1` --- stdout
-   выполняет непосредственный вывод строки

------------------------------------------------------------------------

## 19. exit_group

Завершает процесс (и все его потоки).

------------------------------------------------------------------------

Фактический вывод строки осуществляется единственным системным вызовом:

``` text

```
(man 2 write)

# Разбор системного вызова write

------------------------------------------------------------------------

## Что такое `write()` и почему именно он выводит строку

`printf()` — это библиотечная функция (libc). Она форматирует данные в пользовательской памяти и в итоге
для вывода на `stdout` делает системный вызов `write()`. Поэтому в `strace` видно именно `write(...)` —
это граница перехода из user-space в kernel-space.

Ниже приведён подробный разбор **системного вызова** `write` (см. `man 2 write`).

------------------------------------------------------------------------

## Сигнатура и параметры

```c
ssize_t write(int fd, const void *buf, size_t count);
```

### `fd` — файловый дескриптор
Небольшое целое число — индекс в таблице открытых дескрипторов процесса.

- `0` — stdin
- `1` — stdout
- `2` — stderr
- `>2` — что-то кастомное

В нашем трассе:

```text
write(1, "Hello world\n", 12) = 12
```

`fd = 1`, значит запись идёт в стандартный вывод (обычно терминал).

### `buf` — адрес данных в памяти процесса
Указатель на область пользовательской памяти, откуда ядро будет читать данные для записи.
Это **виртуальный адрес** в адресном пространстве процесса (не “сырой адрес RAM”).

Важно: ядро не доверяет указателю от пользователя — оно проверяет, что память доступна для чтения, и
копирует данные из user-space в kernel-space.

### `count` — число байт
Количество байт, которые требуется записать. `write()` работает с байтами.

В примере `"Hello world\n"` имеет длину 12 байт, поэтому `count = 12`.

------------------------------------------------------------------------

## Возвращаемое значение

Тип результата: `ssize_t`.

- При успехе возвращает **количество реально записанных байт** (может быть меньше `count`).
- При ошибке возвращает `-1` и выставляет `errno`.

В нашем случае:

```text
... = 12
```

означает, что записано ровно 12 байт.

------------------------------------------------------------------------

## Частичная запись (важно)

`write()` **не гарантирует**, что за один вызов запишет все `count` байт.

Частичная запись возможна, например, для:
- pipe/FIFO (буфер ограничен),
- сокетов (сетевые буферы),
- некоторых файловых систем/устройств.

Поэтому если нужно “записать всё”, корректный паттерн — повторять `write()` в цикле, пока не отправим все байты.

------------------------------------------------------------------------

## Типичные ошибки (`errno`)

Наиболее часто встречающиеся причины ошибок:

- `EBADF` — `fd` не открыт или не открыт на запись.
- `EFAULT` — `buf` указывает на недоступную память.
- `EINTR` — вызов прерван сигналом (обычно нужно повторить).
- `EPIPE` — запись в pipe/socket, где читающая сторона закрыта (часто дополнительно приходит `SIGPIPE`).
- `EAGAIN` / `EWOULDBLOCK` — `fd` в non-blocking режиме и сейчас нельзя писать.
- `ENOSPC` — закончилось место на устройстве (обычно для файлов).

------------------------------------------------------------------------

## Как работает `write()` внутри ядра

На x86_64 пользовательский код (или libc) делает инструкцию `syscall` с номером `SYS_write`.
Далее ядро:

1. Находит объект, соответствующий `fd` (файл/tty/pipe/socket).
2. Проверяет права на запись.
3. Проверяет корректность диапазона памяти `[buf, buf+count)`.
4. Копирует данные из памяти процесса.
5. Передаёт данные конкретной реализации записи (для tty/pipe/socket/FS).
6. Возвращает число записанных байт или ошибку.

------------------------------------------------------------------------

## Вывод по нашему эксперименту

В трассе:

```text
write(1, "Hello world\n", 12) = 12
```

именно этот syscall выполняет реальный вывод строки. Все остальные вызовы до него связаны в основном с:
- загрузкой и отображением `libc.so.6` (динамическая линковка),
- настройкой памяти,
- инициализацией runtime.

## Итог и отличия между `hello_printf`, `hello_write`, `hello_syscall`

1. Во всех трёх программах фактический вывод строки выполняется syscall’ом:

```text
write(1, "Hello world\n", 12) = 12
```

2. `hello_write` и `hello_syscall` по `strace` практически одинаковы: оба приводят к одному и тому же системному вызову ядра `write`. Разница лишь в user-space: в одном случае вызывается `write()` (обёртка libc), в другом — `syscall(SYS_write, ...)` (универсальная обёртка libc).

3. `hello_printf` вызывает дополнительные системные вызовы (`fstat(1)`, `getrandom`, дополнительный `brk(...)`) из-за инициализации `stdio`/буферизации и более “тяжёлой” инициализации libc, тогда как прямой `write` этого не требует.

# Итог

Команда `wget kernel.org` активно использует:

-   сетевые системные вызовы (создание и использование TCP-соединения),
-   операции ввода-вывода (чтение из сокета и запись в файл),
-   механизмы управления памятью,
-   инфраструктуру потоков и синхронизации.

Наличие `connect`, `socket`, `recvfrom` и `sendto` подтверждает
установление сетевого соединения и передачу данных.
Вызовы `openat` и `write` связаны с сохранением загруженного файла.
Большое количество `mmap` и `brk` связано с управлением памятью и
загрузкой библиотек.

Ошибки в `openat`, `connect`, `access` являются нормальными и не
означают сбой программы --- они связаны с проверкой альтернативных путей
и сетевыми попытками подключения.

# Разбор функции `syscall()` и реализация без неё

------------------------------------------------------------------------

## Что такое `syscall` и `syscall()`

Важно различать:

-   `syscall` --- это инструкция процессора x86_64, выполняющая переход
    из user-mode в kernel-mode.
-   `syscall()` --- это функция библиотеки libc, являющаяся обёрткой над
    этой инструкцией.

Инструкция `syscall`: - берёт номер системного вызова из регистра RAX, -
берёт аргументы из регистров (RDI, RSI, RDX, R10, R8, R9), - передаёт
управление ядру, - возвращает результат в RAX.

Функция `syscall()` в libc: 1. Раскладывает аргументы по регистрам
согласно ABI Linux x86_64. 2. Выполняет инструкцию `syscall`. 3.
Проверяет результат. 4. При ошибке устанавливает errno и возвращает -1.

------------------------------------------------------------------------

## ABI системных вызовов Linux x86_64

Назначение      Регистр
--------------- ---------
номер syscall   RAX
arg1            RDI
arg2            RSI
arg3            RDX
arg4            R10
arg5            R8
arg6            R9
результат       RAX

Именно поэтому в inline-asm используются constraints: - "a" → RAX - "D"
→ RDI - "S" → RSI - "d" → RDX

------------------------------------------------------------------------

## Inline-asm блок

Пример выполнения системного вызова напрямую:

**asm** volatile ( "syscall" : "=a"(ret) : "a"(nr), "D"(arg1),
"S"(arg2), "d"(arg3) : "rcx", "r11", "memory" );

### Объяснение частей

"a"(nr) --- помещает номер системного вызова в RAX.

"=a"(ret) --- после выполнения берёт значение из RAX и записывает в ret.

"D", "S", "d" --- помещают аргументы в RDI, RSI, RDX.

Clobber list: "rcx", "r11" --- инструкция syscall гарантированно портит
эти регистры. "memory" --- запрещает компилятору переупорядочивать
операции с памятью вокруг системного вызова.

volatile --- запрещает компилятору удалить или агрессивно оптимизировать
данный блок.

------------------------------------------------------------------------

## Как это выглядит в чистом ассемблере

mov rax, 1 mov rdi, 1 lea rsi, \[msg\] mov rdx, 12 syscall

Результат системного вызова возвращается в RAX.

------------------------------------------------------------------------

## Разница между вариантами реализации

Вариант      Как выполняется переход в ядро
------------ ----------------------------------------
write()      libc вызывает syscall внутри
syscall()    libc-обёртка над инструкцией
inline asm   инструкция syscall вызывается напрямую

Во всех случаях в strace отображается один и тот же системный вызов:

write(1, "Hello world`\n`{=tex}", 12) = 12

------------------------------------------------------------------------

## Итог

Функция syscall() --- это небольшая ассемблерная обёртка в libc,
которая: - соблюдает ABI системных вызовов, - выполняет инструкцию
syscall, - обрабатывает ошибки через errno.

В реализации через inline-asm системный вызов выполняется напрямую, без
использования syscall() и без дополнительной логики libc.
