# 3. Базовые понятия, которые нужны для понимания работы

## 3.1 Виртуальная память

Процесс в Linux работает не с физической памятью напрямую, а внутри
собственного **виртуального адресного пространства**.

CPU исполняет инструкции, которые обращаются к **виртуальным адресам**.
Далее эти адреса должны быть переведены в физические адреса памяти. Для
этого используются таблицы страниц и аппаратный MMU.

## 3.2 `task_struct`, `mm_struct`, `vm_area_struct`

У процесса в ядре есть структура `task_struct`. Она описывает сам
процесс как сущность планировщика и ядра.

С адресным пространством процесса связана структура `mm_struct`.

`mm_struct` описывает **всю память процесса**. Внутри него находится:

- информация о сегментах процесса
- текущее значение `brk`
- стартовый адрес стека
- набор VMA
- корень таблиц страниц

Отдельная область памяти описывается структурой
`vm_area_struct` (VMA, Virtual Memory Area).

Одна VMA задаёт:

- начальный виртуальный адрес
- конечный виртуальный адрес
- права доступа
- тип отображения
- связь с файлом или anonymous memory

Важно различать:

- `mm_struct` --- всё адресное пространство процесса целиком
- `vm_area_struct` --- один конкретный регион внутри него

## 3.3 Что показывает `/proc/<pid>/maps`

Файл

```bash
/proc/<pid>/maps
```

показывает **не таблицы страниц** и не фактическое содержимое RAM, а
именно список VMA процесса.

Каждая строка в `maps` соответствует одной области `vm_area_struct`.

То есть `maps` показывает:

- диапазон виртуальных адресов
- права доступа
- привязку к файлу или anonymous mapping

но не показывает напрямую, какие страницы уже реально присутствуют в RAM.

## 3.4 Таблицы страниц и PTE

После того как CPU получает виртуальный адрес, он должен определить,
какой физической странице он соответствует.

Для этого используются **таблицы страниц**.

Таблицы страниц содержат записи, которые обычно называют
**Page Table Entry (PTE)**.

Одна PTE описывает:

- соответствует ли данная виртуальная страница физической странице
- присутствует ли она сейчас
- можно ли её читать
- можно ли её писать
- можно ли её исполнять
- доступна ли она user-mode коду

Важно различать:

- VMA --- логическое описание области памяти
- PTE --- конкретное отображение отдельной виртуальной страницы
- физическая страница --- реальный участок RAM

## 3.5 TLB

**TLB (Translation Lookaside Buffer)** --- это аппаратный кэш переводов
виртуальных адресов в физические.

Если бы CPU каждый раз полностью проходил по таблицам страниц, доступ к
памяти был бы слишком медленным.

Поэтому CPU хранит недавно использованные переводы в TLB.

Когда ядро меняет отображения памяти или права доступа, оно должно
обеспечить согласованность TLB с новыми таблицами страниц.

## 3.6 Что такое `brk`

`brk` --- это механизм, связанный с классической кучей процесса.

Исторически есть понятие **program break** --- граница, отделяющая конец
области данных процесса от свободного пространства над кучей.

При росте кучи через `brk()` ядро сдвигает эту границу вверх, и область
`[heap]` увеличивается.

Современный allocator libc может получать память двумя способами:

- расширять `[heap]` через `brk`
- создавать отдельные отображения через `mmap`

## 3.7 Что такое сегментация

Слово "сегментация" может означать две вещи.

### Исторический смысл

На старых архитектурах память делилась на сегменты с базой и размером.

### Современный практический смысл для Linux

Сейчас основным механизмом является **paging**, а не классическая
сегментация.

Однако слово "segmentation" по-прежнему используется:

- в названии `segmentation fault`
- в разговорном смысле как деление адресного пространства на логические
  области (`text`, `data`, `heap`, `stack`)

Поэтому `segmentation fault` в современных системах фактически означает
фатальную ошибку доступа к виртуальной памяти.

# 4. Общая модель адресного пространства процесса

Ядро представляет память процесса как набор отображений памяти
(**VMA, Virtual Memory Area**), у каждого из которых есть:

- диапазон виртуальных адресов
- права доступа (`r`, `w`, `x`)
- источник отображения (файл или anonymous memory)

Типичные области памяти процесса:

```text
[text / code]      -> машинный код программы
[rodata]           -> read-only данные
[data]             -> инициализированные изменяемые данные
[bss]              -> неинициализированные данные
[heap]             -> куча
[mmap regions]     -> библиотеки, файлы, anonymous mappings
[stack]            -> стек вызовов функций
[vdso/vvar]        -> специальные области ядра
```

Файл

```bash
/proc/<pid>/maps
```

показывает runtime-состояние этих областей именно на уровне VMA.

# 5. Что такое page fault

## 5.1 Общее определение

**Page fault** --- это аппаратное исключение, которое возникает, когда
текущая инструкция процессора обращается к виртуальному адресу, а это
обращение нельзя выполнить немедленно.

Причины бывают двух типов.

### Исправимый fault

Обращение в принципе допустимо, но страница ещё не подготовлена:

- нет подходящей PTE
- физическая страница ещё не выделена
- anonymous mapping ещё не материализован
- нужна обработка copy-on-write

### Фатальный fault

Обращение недопустимо:

- адрес не попадает ни в одну VMA
- нарушены права доступа
- произошёл выход за допустимую область стека
- попытка записи идёт в read-only страницу
- попытка доступа идёт в `PROT_NONE`

В исправимом случае ядро может подготовить страницу и вернуть
управление процессу.

В фатальном случае процесс обычно получает `SIGSEGV`.

## 5.2 Что делает CPU при page fault

Когда процессор выполняет инструкцию чтения, записи или исполнения:

1. он пытается перевести виртуальный адрес в физический
2. проверяет права доступа
3. если перевод или права не позволяют выполнить доступ, генерирует
   page fault
4. управление передаётся в обработчик fault в ядре

## 5.3 Что делает ядро при page fault

Ядро анализирует:

- какой адрес вызвал fault
- какой тип доступа выполнялся
- есть ли подходящая VMA
- допускает ли VMA такой доступ
- можно ли подготовить страницу

Дальше есть два варианта:

- fault обслуживается: создаётся PTE, выделяется физическая страница,
  обновляются таблицы страниц, выполнение продолжается
- fault признаётся недопустимым: процесс получает `SIGSEGV`

# 6. Первая часть работы: exec самой себя

По условию нужно написать программу, которая:

1. выводит `pid`
2. ждёт одну секунду
3. делает `exec(2)` самой себя
4. выводит сообщение `Hello world`

## 6.1 Что делает `exec`

Системный вызов `exec*()` **не создаёт новый процесс**.

Он делает другое:

- сохраняет существующий `pid`
- уничтожает старый образ процесса
- загружает новый образ исполняемого файла
- создаёт заново код, данные, стек, кучу и отображения библиотек
- передаёт управление новой точке входа программы

То есть:

- процесс остаётся тем же
- адресное пространство становится новым

## 6.2 Что реально вызывается

В программе используется `execl()`. Это библиотечная функция libc.

На низком уровне она подготавливает массив аргументов и приводит к
системному вызову семейства `execve`.

То есть:

- `execl()` --- обёртка libc
- `execve()` --- переход в ядро

## 6.3 Что делает CPU и ядро при exec

До вызова `exec` код работает в user mode.

При входе в системный вызов происходит:

- переход CPU из user mode в kernel mode
- передача управления обработчику system call
- работа ядра с исполняемым файлом

Далее ядро:

- открывает исполняемый файл
- проверяет его формат
- подготавливает новый userspace image
- удаляет старые user-space отображения процесса
- создаёт новые VMA под код, данные, стек и библиотеки
- инициализирует новый пользовательский стек (`argc`, `argv`, `envp`)
- ставит instruction pointer на entry point новой программы

## 6.4 Что наблюдалось

При запуске программы вывод был вида:

```text
pid = 12345
About to exec myself...
pid = 12345
Hello world
```

Главное наблюдение:

- `pid` до и после `exec` одинаковый
- значит новый процесс не создавался

При этом `/proc/<pid>/maps` описывает уже **новое адресное пространство**.

## 6.5 Почему адреса после exec могут отличаться

Даже если исполняется тот же бинарный файл, адреса отображений могут быть
другими из-за **ASLR** (Address Space Layout Randomization).

Это означает, что:

- код программы
- библиотеки
- стек
- куча

могут попасть по другим виртуальным адресам при новом запуске образа.

## 6.6 Вывод по части с exec

`exec()` заменяет образ текущего процесса, но не меняет `pid`.

Поэтому верная интерпретация такая:

- это тот же процесс
- но с новым адресным пространством

# 8. Стек

## 8.1 Что делалось

Была написана рекурсивная функция, которая на каждом вызове:

- выделяла локальный массив на стеке
- записывала в него данные
- печатала адрес массива
- рекурсивно вызывала себя

Пример идеи:

```c
volatile char buf[4096];
memset((void *)buf, depth, sizeof(buf));
```

## 8.2 Что такое стек

Стек используется для:

- локальных автоматических переменных
- адресов возврата
- сохранённых регистров
- служебной информации вызова функций

Для каждой активной функции обычно существует отдельный **stack frame**.

## 8.3 Что происходит на низком уровне

Выделение локального массива на стеке --- это не системный вызов.

Обычно происходит следующее:

- компилятор формирует код функции
- при входе в функцию изменяется stack pointer
- под локальные переменные резервируется место в stack frame
- запись в массив выполняется обычными инструкциями CPU

Пока используемые адреса попадают в уже доступную часть стека, ядро в
этом не участвует.

## 8.4 Почему стек растёт вниз

При рекурсии адреса локального массива изменялись в сторону уменьшения.

Это означает, что стек на данной архитектуре растёт **вниз**, то есть к
меньшим адресам.

Типичная картина:

```text
depth=0  buf=0x7fff...
depth=1  buf=0x7fff... ниже
depth=2  buf=0x7fff... ещё ниже
```

## 8.5 Как ядро расширяет стек

Если процесс начинает обращаться к адресу ниже уже подготовленной части
стека, CPU генерирует page fault.

Далее ядро проверяет:

- относится ли адрес к стековой области
- допустим ли такой рост стека
- не превышен ли лимит `RLIMIT_STACK`
- нет ли пересечения с соседними VMA

Если fault признаётся допустимым ростом стека, ядро:

- расширяет stack VMA вниз
- подготавливает новые записи в таблицах страниц
- выделяет реальные страницы по мере необходимости
- возвращает управление процессу

После этого инструкция повторяется и успешно выполняется.

## 8.6 Почему [stack] в maps мог почти не меняться

Важное наблюдение: область `[stack]` в `/proc/<pid>/maps` не обязана
заметно меняться при небольшой рекурсии.

Причина в том, что:

- стек уже может быть отображён достаточно большим регионом
- страницы выделяются лениво
- программа может использовать уже существующую часть stack mapping

Поэтому возможны две ситуации:

1. адреса локальных переменных явно уходят вниз
2. а строка `[stack]` в `maps` при этом почти не меняется

Это не ошибка, а нормальное поведение.

## 8.7 Когда рост стека становится заметнее

Если увеличить:

- глубину рекурсии
- размер локального массива

то вероятность увидеть изменение stack-region в `maps` становится выше.

## 8.8 Вывод по стеку

Рекурсия расходует стек, а локальные массивы функций размещаются в
stack frame'ах.

Адреса локальных буферов уменьшаются по мере углубления рекурсии, что
соответствует росту стека вниз по адресам.

# 9. Куча

## 9.1 Что делалось

После эксперимента со стеком программа в цикле выделяла память через
`malloc()`.

На каждой итерации:

- выделялся новый блок
- блок заполнялся
- печатался его адрес
- делалась пауза

После этого блоки освобождались через `free()`.

## 9.2 Что такое куча

Куча --- это область динамической памяти процесса, из которой allocator
выдаёт блоки при вызове `malloc()`.

Куча отличается от:

- `.data`
- `.bss`
- стека

потому что она используется для объектов, создаваемых динамически во
время выполнения программы.

## 9.3 Что делает `malloc` на низком уровне

`malloc()` сам по себе не является системным вызовом.

Это функция allocator'а libc. Сначала allocator пытается найти
подходящий свободный chunk в уже имеющихся структурах.

Если памяти allocator'у не хватает, он может обратиться к ядру:

- через `brk()` для расширения `[heap]`
- через `mmap()` для отдельного отображения

То есть часть вызовов `malloc()` может происходить полностью в user
space, без перехода в ядро.

## 9.4 Что такое chunk

Allocator работает не просто с "сырыми указателями", а с внутренними
блоками памяти, которые часто называют **chunk**.

Обычно у chunk есть:

- служебные метаданные
- пользовательская область, которую и получает программа

Именно поэтому `free()` требует передавать ровно тот адрес, который
вернул `malloc()`.

## 9.5 Что наблюдалось

При последовательных вызовах `malloc()` можно было увидеть:

- либо расширение области `[heap]`
- либо появление дополнительных anonymous mappings

На практике для умеренных размеров часто растёт именно `[heap]`.

## 9.6 Что делает `free`

`free()` тоже обычно не является системным вызовом.

Allocator:

- помечает chunk свободным
- может объединять соседние свободные блоки
- может кэшировать его для повторного использования
- иногда может вернуть память ядру, но не обязан делать это сразу

## 9.7 Почему после free heap может не уменьшаться

После `free()` память освобождается не обязательно для ядра, а прежде
всего для самого allocator'а.

Это означает:

- chunk считается свободным
- allocator может использовать его повторно
- но отображение `[heap]` может остаться прежним

Поэтому вполне нормально, что после `free()` в `/proc/<pid>/maps`
область `[heap]` визуально почти не меняется.

## 9.8 Вывод по куче

`malloc()` изменяет динамическую память процесса, а `free()` не обязан
немедленно уменьшать `[heap]`.

Освобождение памяти означает прежде всего возврат блока allocator'у, а
не обязательно немедленный возврат памяти ядру.

# 10. Анонимное отображение через mmap

## 10.1 Что делалось

Программа создавала новый регион адресов размером в 10 страниц через:

```c
mmap(NULL, 10 * page_size,
     PROT_READ | PROT_WRITE,
     MAP_PRIVATE | MAP_ANONYMOUS,
     -1, 0);
```

## 10.2 Что означает MAP_ANONYMOUS

`MAP_ANONYMOUS` означает, что отображение:

- не связано с файлом
- создаётся как отдельный anonymous region
- существует только как область памяти процесса

## 10.3 Что делает ядро при mmap

`mmap()` --- это системный вызов.

Ядро при его обработке:

- ищет подходящий свободный диапазон виртуальных адресов
- создаёт новый `vm_area_struct`
- выставляет для него нужные флаги доступа
- вставляет VMA в адресное пространство процесса

Важно: это ещё не означает, что все физические страницы уже выделены.

Сначала создаётся виртуальная область. Реальные страницы часто
подключаются только при первом обращении к ним через page fault.

## 10.4 Что наблюдалось в maps

После вызова `mmap()` в `/proc/<pid>/maps` появлялся новый регион вида:

```text
7f...-7f... rw-p 00000000 00:00 0
```

Он соответствует созданному anonymous mapping.

## 10.5 Вывод по mmap

`mmap()` позволяет присоединять к процессу новые области виртуальной
памяти, независимо от классической кучи.

------------------------------------------------------------------------

# 11. Изменение прав доступа через mprotect

## 11.1 Что делалось

Для созданного anonymous region права доступа изменялись при помощи
`mprotect()`.

Использовались два режима:

1. `PROT_NONE`
2. `PROT_READ`

После этого выполнялись намеренно некорректные обращения к региону.

## 11.2 Что такое mprotect

`mprotect(addr, len, prot)` изменяет права доступа к уже существующему
отображению памяти.

Возможные права:

- `PROT_READ`
- `PROT_WRITE`
- `PROT_EXEC`
- `PROT_NONE`

## 11.3 Что делает ядро при mprotect

`mprotect()` --- это системный вызов.

Ядро:

- находит VMA, который пересекается с данным диапазоном
- при необходимости делит его на части
- меняет флаги доступа у соответствующего диапазона
- обновляет права в таблицах страниц
- обеспечивает согласованность TLB с новыми правами

Именно поэтому после `mprotect()` меняется не только логика VMA, но и
аппаратно видимые свойства отображения.

## 11.4 Что наблюдалось при PROT_NONE

После установки `PROT_NONE` чтение из региона запрещалось полностью.

Попытка чтения приводила к завершению дочернего процесса по сигналу
`SIGSEGV`.

Типичный результат:

```text
child read terminated by signal 11
```

## 11.5 Что наблюдалось при PROT_READ

После установки `PROT_READ` регион становился доступен только для чтения.

Попытка записи в него снова приводила к `SIGSEGV`:

```text
child write terminated by signal 11
```

## 11.6 Почему ошибки проверялись в дочернем процессе

Если бы запрещённый доступ выполнялся в основном процессе, программа
завершилась бы сразу и эксперимент нельзя было бы продолжить.

Поэтому для наглядности использовался `fork()`:

- дочерний процесс нарушает права
- получает `SIGSEGV`
- родитель наблюдает это через `waitpid()`
- родитель продолжает работу

## 11.7 Что видно в maps

После `mprotect()` у региона меняются права.

Например:

- `rw-p` -> `---p`
- `rw-p` -> `r--p`

Это и есть отражение нового режима доступа к страницам.

# 12. Segmentation fault

## 12.1 Что это такое

**Segmentation fault** --- это аварийное завершение процесса из-за
недопустимого обращения к памяти.

Обычно это означает:

- обращение по неверному адресу
- обращение к unmapped region
- чтение или запись с нарушением прав доступа страницы

В Linux это обычно выражается как получение сигнала:

```text
SIGSEGV
```

## 12.2 Что происходит на низком уровне

Недопустимый доступ выполняет обычная инструкция CPU.

Далее:

- CPU обнаруживает, что адрес недопустим или нарушены права
- генерирует page fault
- ядро анализирует причину fault
- если исправить его нельзя, процесс получает `SIGSEGV`

То есть `segmentation fault` --- это не отдельный "магический" механизм,
а результат того, что fault признан фатальным.

## 12.3 Как это проявилось в работе

В данной работе `segmentation fault` наблюдался при:

- чтении из региона с `PROT_NONE`
- записи в регион с `PROT_READ`

То есть в обоих случаях процесс нарушал права доступа к страницам.

## 12.4 Вывод

`SIGSEGV` возникает не только из-за "плохого указателя", но и при
корректном адресе, если сам доступ запрещён установленными правами
страницы.

# 13. Частичное удаление отображения через munmap

## 13.1 Что делалось

Из созданного 10-страничного региона были отсоединены страницы с 4 по 6.

Если считать страницы с единицы, то удалялся средний кусок длиной в 3
страницы.

## 13.2 Что делает munmap

`munmap(addr, len)` удаляет отображение памяти в указанном диапазоне.

Если диапазон покрывает не весь region, возможны варианты:

- удаление начала
- удаление конца
- удаление середины

В случае удаления середины один region может распасться на два.

## 13.3 Что делает ядро при munmap

`munmap()` --- это системный вызов.

Ядро:

- находит VMA, пересекающийся с диапазоном
- удаляет соответствующий участок
- если удаляется середина, разрезает один VMA на два
- убирает соответствующие PTE
- освобождает связанные ресурсы
- обновляет состояние TLB

## 13.4 Что наблюдалось

До вызова `munmap()` в `maps` был один непрерывный anonymous region.

После удаления страниц 4--6 регион распался на две части:

- первая часть до удалённого диапазона
- вторая часть после удалённого диапазона

В `maps` это видно как две отдельные строки вместо одной.

## 13.5 Почему так происходит

Потому что ядро оперирует отображениями памяти как VMA-областями.

Если удалить кусок посередине VMA, ядро создаёт две новые области из
остатков исходного отображения.

## 13.6 Вывод по munmap

`munmap()` умеет не только удалять region целиком, но и разрезать одно
отображение на несколько частей.

------------------------------------------------------------------------

# 14. Что происходило с адресным пространством в ходе всей работы

Полная последовательность изменений была такой:

1. процесс стартовал и имел исходное адресное пространство
2. при `exec()` старый образ процесса был заменён новым
3. при рекурсии расходовался стек
4. при `malloc()` использовалась куча
5. при `free()` память возвращалась allocator'у
6. при `mmap()` появился новый anonymous region
7. при `mprotect()` у него менялись права доступа
8. при нарушении этих прав дочерний процесс получал `SIGSEGV`
9. при `munmap()` середины region распался на две части

Это показывает, что адресное пространство процесса не является
фиксированным: оно динамически изменяется во время выполнения программы.

# 15. Наблюдение через /proc/<pid>/maps

Для наблюдения использовались команды:

```bash
cat /proc/<pid>/maps
```

```bash
watch -n 0.5 -d cat /proc/<pid>/maps
```

```bash
watch -n 0.5 -d 'grep -E "\[heap\]|\[stack\]|00:00" /proc/<pid>/maps'
```

Что полезно отслеживать:

объект в maps      что показывает
------------------- -------------------------------------------
`[stack]`           стек процесса
`[heap]`            куча процесса
`rw-p 00:00 0`      anonymous region с записью
`r--p 00:00 0`      anonymous region только для чтения
`---p 00:00 0`      region без прав доступа

# 16. Практические замечания по наблюдению

## 16.1 Почему нужны большие паузы

Изменения address space происходят быстро, поэтому для наблюдения
удобно ставить паузы между этапами.

Без пауз можно просто не успеть заметить:

- изменение прав
- появление нового region
- разделение region после `munmap()`

## 16.2 Почему стек может быть не очень заметен в maps

Небольшая рекурсия может не привести к заметному изменению строки
`[stack]`, хотя сами адреса локальных массивов уже показывают движение
стека вниз.

## 16.3 Почему лучше использовать watch -n 0.5

Стандартный интервал `watch` часто слишком большой для такой работы.

Поэтому удобнее:

```bash
watch -n 0.5 -d cat /proc/<pid>/maps
```

# 17. Выводы

В ходе работы было установлено следующее.

1.  `exec()` не создаёт новый процесс, а заменяет образ текущего.
2.  При `exec()` `pid` сохраняется, но адресное пространство
    пересоздаётся.
3.  `mm_struct` описывает всё адресное пространство процесса, а
    `vm_area_struct` --- отдельные области памяти внутри него.
4.  `/proc/<pid>/maps` показывает список VMA, а не фактическое состояние
    всех физических страниц.
5.  Стек используется для локальных автоматических объектов и растёт вниз
    по адресам.
6.  Небольшая рекурсия не обязана заметно менять строку `[stack]` в
    `maps`.
7.  Page fault может быть как исправимым, так и фатальным.
8.  При допустимом росте стека ядро может расширять стековую область
    вниз и подготавливать новые страницы.
9.  `malloc()` использует динамическую память процесса, связанную с heap
    и/или дополнительными mapping'ами.
10. `free()` не обязан немедленно уменьшать `[heap]`.
11. `mmap(MAP_ANONYMOUS)` создаёт новый region виртуальной памяти.
12. `mprotect()` меняет права доступа к страницам уже существующего
    отображения.
13. Нарушение прав доступа приводит к `SIGSEGV` (`segmentation fault`).
14. `munmap()` может удалить часть отображения и разрезать region на
    несколько отдельных VMA.
15. `TLB` является аппаратным кэшем переводов виртуальных адресов в
    физические и должен быть согласован с новыми таблицами страниц при
    изменении отображений.

# 18. Возможные вопросы на защите

## Почему после exec pid не изменился?

Потому что `exec()` не создаёт новый процесс. Он лишь заменяет образ
существующего процесса.

## В чём разница между `mm_struct` и `vm_area_struct`?

`mm_struct` описывает всё адресное пространство процесса, а
`vm_area_struct` описывает один отдельный регион внутри него.

## Что показывает `/proc/<pid>/maps`?

Он показывает список VMA процесса: диапазоны адресов, права доступа и
источники отображений.

## В чём разница между VMA и реальными страницами?

VMA задаёт логический диапазон адресов и его свойства, а реальные
страницы появляются через таблицы страниц и page fault по мере
обращения к памяти.

## Что такое PTE?

Это запись таблицы страниц, описывающая отображение одной виртуальной
страницы в физическую и её права доступа.

## Что такое page fault?

Это исключение CPU при невозможности немедленно выполнить обращение к
виртуальной памяти. Ядро либо обслуживает его, либо завершает процесс
сигналом `SIGSEGV`.

## Как ядро расширяет стек?

Если fault-адрес распознаётся как допустимый рост стека, ядро расширяет
стековую VMA вниз, подготавливает таблицы страниц и позволяет процессу
продолжить выполнение.

## Почему стек не всегда явно "растёт" в maps?

Потому что часть stack-region может быть уже отображена заранее, а новые
страницы выделяются лениво.

## Что такое `brk`?

Это механизм роста классической кучи процесса за счёт сдвига program
break.

## Что такое TLB?

Это аппаратный кэш переводов виртуальных адресов в физические, который
ускоряет доступ к памяти.

## Почему после free heap может не уменьшаться?

Потому что освобождение памяти происходит сначала на уровне allocator'а,
а не обязательно немедленно на уровне ядра.

## Почему запрещённые обращения лучше делать в дочернем процессе?

Чтобы основной процесс не завершился по `SIGSEGV` и можно было
продолжить эксперимент.

## Что означает signal 11?

Это `SIGSEGV`, то есть недопустимый доступ к памяти.

## Почему после удаления середины region стало два?

Потому что `munmap()` удалил центральную часть VMA, и ядро разделило
исходное отображение на два независимых региона.
